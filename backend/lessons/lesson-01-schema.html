ออกแบบฐานข้อมูล: อ่าน schema.sql ให้เข้าใจ

ฐานข้อมูลนี้มี 8 ตาราง ไฟล์ schema.sql อธิบายโครงสร้างทั้งหมดในไฟล์เดียว บทนี้จะดูว่าแต่ละตารางทำหน้าที่อะไร และทำไมต้องเขียนกฎแบบนี้

เป้าหมายบทนี้

  • อธิบายความสัมพันธ์ระหว่าง 8 ตารางได้
  • อ่านคำสั่ง FOREIGN KEY, UNIQUE, ENUM และ ON DELETE CASCADE ได้
  • ทำนายได้ว่าการลบข้อมูลหนึ่งแถวจะกระทบตารางใดบ้าง

ภาพรวม 8 ตาราง

ตารางลูกจะอ้างถึงตารางแม่ผ่าน FOREIGN KEY ดูจากกล่องด้านล่าง ตารางที่มี FK คือตารางที่อ้างถึงตารางอื่น

users

  • ผู้ใช้ทุกคน แยกด้วย role
  • ไม่มี FK

periods

  • รอบการประเมิน มีวันเปิด-ปิด
  • ไม่มี FK

topics FK

  • หัวข้อ อยู่ในรอบ
  • อ้างถึง periods

indicators FK

  • ตัวชี้วัด อยู่ในหัวข้อ
  • อ้างถึง topics

assignments FK

  • กรรมการ 1 คน ประเมินผู้รับ 1 คน ในรอบ 1 รอบ
  • อ้างถึง periods, users (2 ครั้ง)

self_scores FK

  • คะแนนที่ผู้รับประเมินตนเอง
  • อ้างถึง users, indicators

self_details FK

  • รายละเอียดและหลักฐาน
  • อ้างถึง users, indicators

scores FK

  • คะแนนที่กรรมการให้
  • อ้างถึง assignments, indicators

อ่านโค้ดจริงทีละส่วน

1) ตารางแม่ต้องถูกสร้างก่อนตารางลูก

ไฟล์เขียนไว้บรรทัดแรกว่า "อ่านจากบนลงล่าง" เพราะ FOREIGN KEY ต้องอ้างถึงตารางที่มีอยู่แล้ว

-- schema.sql:2
-- อ่านจากบนลงล่าง: ตารางลูกอ้างถึงตารางแม่ด้วย FOREIGN KEY

ไฟล์ seed.js บรรทัด 9–11 รันคำสั่งทีละคำสั่งตามลำดับนี้

2) ENUM จำกัดค่าที่เป็นไปได้

role        ENUM('admin','evaluatee','evaluator')      -- schema.sql:12
score_type  ENUM('yesno','scale')                       -- schema.sql:40
status      ENUM('pending','draft','confirmed')         -- schema.sql:53

ค่าที่นอกเหนือจากนี้จะถูกฐานข้อมูลปฏิเสธ ค่า role ที่ใช้ในโค้ดตรงกับ ENUM ทุกตัว

3) UNIQUE กันข้อมูลซ้ำ

UNIQUE (period_id, evaluatee_id, evaluator_id)  -- schema.sql:56  มอบหมายซ้ำไม่ได้
UNIQUE (assignment_id, indicator_id)             -- schema.sql:91  ให้คะแนนตัวชี้วัดเดิมซ้ำไม่ได้

เมื่อซ้ำ MySQL ส่ง ER_DUP_ENTRY แล้ว server.js บรรทัด 37 แปลงเป็น HTTP 400 พร้อมข้อความ "ข้อมูลซ้ำกับที่มีอยู่แล้ว"

4) ON DELETE CASCADE ลบตามลำดับชั้น

ลบแถวในตารางแม่ ฐานข้อมูลจะลบแถวลูกที่อ้างถึงมันให้อัตโนมัติ ลองดูผลจากตัวจำลองด้านล่าง

ลองลบแล้วดูว่าอะไรหายตาม

กดตารางที่ต้องการลบ ระบบจะคำนวณว่าตารางใดจะถูกลบตาม cascade บ้าง

หมายเหตุ: ตัวจำลองนี้ดูเฉพาะความสัมพันธ์ FOREIGN KEY ตามที่เขียนใน schema.sql ไม่ได้รันฐานข้อมูลจริง และไม่ได้ดูว่าโค้ด route ทำอะไรเพิ่มเติม

แบบทดสอบสั้น

ข้อ 1: ตารางใดต่อไปนี้ ไม่มี FOREIGN KEY

users ไม่อ้างถึงตารางอื่น จึงไม่มี FOREIGN KEY ส่วน periods ก็ไม่มีเช่นกัน

ข้อ 2: ค่าใดต่อไปนี้ ไม่ผ่าน ENUM ของ role

ENUM ยอมรับเฉพาะ 'admin', 'evaluatee', 'evaluator' เท่านั้น

ข้อ 3: ถ้าลบ users หนึ่งแถว แถวใน scores ที่เกี่ยวข้องจะถูกลบด้วยหรือไม่

ลบ user จะลบ assignments ที่เขาเป็นผู้รับหรือกรรมการ และ assignments ลบ scores ต่อ จึงถูกลบเป็นทอด ๆ

แบบฝึกหัด: เพิ่มตารางใหม่

เขียน CREATE TABLE ของตาราง committee_notes ที่เก็บหมายเหตุของกรรมการ โดยมี assignment_id เป็น FOREIGN KEY, คอลัมน์ note TEXT NOT NULL และ created_at ที่ค่าเริ่มต้นเป็นเวลาปัจจุบัน

เฉลย 
CREATE TABLE IF NOT EXISTS committee_notes (
  id INT AUTO_INCREMENT PRIMARY KEY,
  assignment_id INT NOT NULL,
  note TEXT NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (assignment_id) REFERENCES assignments(id) ON DELETE CASCADE
);

เมื่อพิมพ์เสร็จให้เทียบกับเฉลย จุดที่ควรตรวจคือ FOREIGN KEY, ON DELETE CASCADE และค่า DEFAULT ของ created_at

สิ่งที่ schema ไม่ได้ป้องกัน

score INT ใน schema ไม่มีการจำกัดช่วงค่า ฐานข้อมูลจะรับคะแนนเป็น 99 หรือ -3 ได้ การตรวจช่วงคะแนน (0–1 สำหรับ yesno และ 1–4 สำหรับ scale) อยู่ในฟังก์ชัน validScore ใน helpers.js บรรทัด 21–24 และถูกเรียกใช้ใน routes/self.js และ routes/evaluate.js

ผลที่ตามมาคือ ถ้ามีโค้ดอื่นเขียนลงตาราง scores โดยไม่ผ่านฟังก์ชันนี้ ข้อมูลผิดจะเข้าไปได้ และจะไม่มีใครเตือน บทนี้ใช้เป็นคำถามทบทวนได้: กฎสำคัญควรอยู่ที่ schema หรือที่โค้ด และแต่ละแบบมีข้อดีข้อเสียอย่างไร
