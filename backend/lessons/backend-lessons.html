บทที่ 1: ออกแบบฐานข้อมูล (schema.sql)

ฐานข้อมูลมี 8 ตาราง ความสัมพันธ์ทั้งหมดอยู่ในไฟล์เดียว อ่านจากบนลงล่างตามลำดับที่ไฟล์เขียนไว้

1. ก่อนเขียนโค้ด ต้องรู้ว่าระบบจะจำอะไร

ฐานข้อมูลคือที่เก็บความจริงของระบบ ทุกอย่างที่ระบบต้องจำ เช่น ผู้ใช้ รอบประเมิน คะแนน จะต้องมีตารางรองรับ การออกแบบตารางก่อนจึงเป็นการตัดสินใจว่า "ข้อมูลอะไรเป็นของอะไร" และ "ห้ามอะไรเกิดขึ้น"

2. ความรู้พื้นฐานที่ใช้ใน schema.sql

  • ตาราง (table) เก็บข้อมูลเป็นแถว แต่ละแถวมีคอลัมน์ตามที่ประกาศ
  • ชนิดข้อมูล INT เก็บตัวเลขจำนวนเต็ม VARCHAR(n) เก็บข้อความไม่เกิน n ตัว TEXT เก็บข้อความยาว DECIMAL(6,2) เก็บทศนิยมแบบแม่นยำ DATE เก็บวันที่ และ BOOLEAN เก็บจริง/เท็จ
  • PRIMARY KEY AUTO_INCREMENT ให้ทุกแถวมีเลขประจำตัวที่ไม่ซ้ำและเพิ่มให้เอง
  • NOT NULL และ DEFAULT NOT NULL ห้ามเว้นว่าง DEFAULT คือค่าที่ใส่ให้เมื่อโค้ดไม่ได้ส่งค่านั้นมา
  • ENUM จำกัดค่าให้เป็นได้เฉพาะรายการที่ระบุ
  • UNIQUE ห้ามค่าซ้ำ ทั้งคอลัมน์เดียวหรือหลายคอลัมน์รวมกัน
  • FOREIGN KEY บอกว่าคอลัมน์นี้ต้องชี้ไปยังแถวที่มีอยู่จริงในตารางแม่
  • ON DELETE CASCADE เมื่อแถวแม่ถูกลบ แถวลูกที่ชี้มาจะถูกลบตาม
CREATE TABLE IF NOT EXISTS topics (
  id INT AUTO_INCREMENT PRIMARY KEY,
  period_id INT NOT NULL,
  name VARCHAR(150) NOT NULL,
  FOREIGN KEY (period_id) REFERENCES periods(id) ON DELETE CASCADE
);

อ่านได้ว่า: หัวข้อ 1 แถวต้องอยู่ในรอบที่มีจริง 1 รอบ และถ้ารอบถูกลบ หัวข้อนั้นก็หายไปด้วย

3. ความสัมพันธ์แบบหนึ่งต่อหลาย

รอบหนึ่งมีหลายหัวข้อ หัวข้อหนึ่งมีหลายตัวชี้วัด และการมอบหมายหนึ่งแถวผูกกรรมการคนหนึ่งกับผู้รับคนหนึ่งในรอบหนึ่ง ความสัมพันธ์เหล่านี้ทำด้วย FOREIGN KEY ฝั่งลูก เสมอ ตารางแม่จึงต้องถูกสร้างก่อนเสมอ

4. ขีดจำกัดของ schema

schema ไม่ได้บังคับทุกกฎ เช่น คอลัมน์ score เป็น INT ธรรมดา ไม่รู้ว่าช่วงที่ถูกต้องคือ 0–1 หรือ 1–4 กฎนั้นจึงต้องอยู่ในโค้ด ผู้ออกแบบต้องเลือกว่ากฎไหนควรอยู่ในฐานข้อมูล (ทุกโปรแกรมที่เขียนลงตารางจะถูกคุ้มครอง) และกฎไหนอยู่ในโค้ด (ยืดหยุ่นกว่า แต่ถ้าโค้ดอื่นลืมตรวจ ข้อมูลผิดจะเข้าได้)

อ่านโค้ดจริงทีละบรรทัด

แต่ละบรรทัดมีคำแปลภาษาพูดด้านข้าง อ่านให้เข้าใจก่อนไปทำแบบฝึกพิมพ์

ลองลบแล้วดูว่าอะไรหายตาม

    บทที่ 2: เชื่อมต่อฐานข้อมูล เซิร์ฟเวอร์ และฟังก์ชันช่วย

    ทุกไฟล์ใช้ query() จาก db.js และ ok/error/percent จาก helpers.js ส่วน server.js ต่อทุกอย่างเข้าด้วยกัน

    1. เส้นทางของ request หนึ่งครั้ง

    เมื่อหน้าเว็บส่ง request มาที่ /api/periods Express จะวิ่งผ่านรายการ middleware ตามลำดับที่ลงทะเบียนไว้ใน server.js ถ้า middleware ตัวไหนเรียก next() ก็วิ่งต่อ ถ้าตอบ response เองหรือส่ง error ก็หยุด ลำดับจึงสำคัญมาก เช่น ต้อง login ก่อนค่อยตรวจบทบาท

    2. Promise และ async/await

    การอ่านฐานข้อมูลใช้เวลา ฟังก์ชัน query() จึงคืน Promise ซึ่งเป็น "สัญญาว่าจะได้ผลในอนาคต" คำว่า await หมายถึงรอให้สัญญานั้นเสร็จก่อนค่อยใช้ผลลัพธ์ ถ้าลืม await ตัวแปรจะได้ Promise ที่ยังไม่มีค่า ไม่ใช่แถวข้อมูล

    const rows = await query('SELECT * FROM users WHERE id = ?', [id]); // ได้ผลจริง
const rows = query('SELECT * FROM users WHERE id = ?', [id]);         // ได้ Promise ยังไม่มีผล

    3. Connection pool

    การเปิดการเชื่อมต่อฐานข้อมูลใหม่ทุกครั้งช้ามาก pool เก็บการเชื่อมต่อไว้ใช้ซ้ำ แต่ละ request ยืมไปใช้แล้วคืน mysql.createPool จึงถูกสร้างครั้งเดียวในไฟล์ db.js และทุกไฟล์ใช้ query() ร่วมกัน

    4. Parameter ? ป้องกัน SQL injection

    ห้ามนำค่าจากผู้ใช้ไปต่อเป็นข้อความ SQL เพราะผู้ใช้อาจส่งข้อความที่เปลี่ยนความหมายของคำสั่งได้ ให้ใช้เครื่องหมาย ? แล้วส่งค่าแยกเป็นอาร์เรย์เสมอ ไดรเวอร์จะจัดการการหลบอักขระให้

    // ไม่ปลอดภัย: ค่าจากผู้ใช้ถูกต่อเข้าไปตรง ๆ
query("SELECT * FROM users WHERE username = '" + username + "'");
// ปลอดภัย: ค่าถูกส่งแยกเป็นพารามิเตอร์
query('SELECT * FROM users WHERE username = ?', [username]);

    5. Error handler

    Express 5 ส่ง error จาก async function ไปยัง middleware ที่มี 4 พารามิเตอร์ (err, req, res, next) ให้อัตโนมัติ ทำให้ route ไม่ต้องเขียน try/catch ทุกตัว ไฟล์นี้จึงแปลง error ที่รู้จักเป็นรหัสตอบกลับที่เหมาะสมไว้ที่จุดเดียว

    6. รูปแบบการตอบกลับที่คงที่

    helpers.js กำหนดว่าทุกการตอบกลับมีรูปแบบ { status, message, data } หน้าเว็บจึงอ่านผลได้เหมือนกันทุก endpoint

    บทที่ 3: ยืนยันตัวตนและสิทธิ์

    auth.js ออก ตรวจ และควบคุม token ส่วน routes/auth.js เป็น endpoint ที่ผู้ใช้เรียกจริง

    1. Authentication กับ Authorization

    Authentication คือการยืนยันว่า "คุณคือใคร" ส่วน Authorization คือการตัดสินว่า "คุณทำอะไรได้" ระบบนี้ทำทั้งสองอย่าง ไฟล์ auth.js ทำ authentication ด้วย token และ allow() ทำ authorization ด้วยบทบาท

    2. แฮชรหัสผ่านด้วย bcrypt

    รหัสผ่านต้องไม่ถูกเก็บเป็นข้อความตรง ๆ แฮชคือการแปลงข้อมูลเป็นค่าสรุปทางเดียว ย้อนกลับไม่ได้ เวลาตรวจรหัสผ่านจะแฮชรหัสที่ผู้ใช้กรอกแล้วเทียบกับค่าที่เก็บไว้ bcrypt เพิ่ม salt สุ่มให้แต่ละรหัส จึงแฮชเดียวกันสองครั้งจะได้ผลต่างกัน

    const hash = await bcrypt.hash('admin1234', 10);   // เก็บค่านี้ลงฐานข้อมูล
const ok = await bcrypt.compare('admin1234', hash); // ได้ true

    3. JWT คืออะไร

    JWT คือข้อความที่มี 3 ส่วนคั่นด้วยจุด ได้แก่ header, payload และ signature payload ในระบบนี้เก็บ id, role และสถานะต้องเปลี่ยนรหัส ส่วน signature ถูกคำนวณจาก SECRET เมื่อเซิร์ฟเวอร์ได้รับ token จะตรวจ signature ถ้าใครแก้ payload ก็ตรวจไม่ผ่าน

    token ถูกออกแบบให้หมดอายุเองภายใน 8 ชั่วโมง เซิร์ฟเวอร์ไม่ได้จำว่าใคร login อยู่ จึงไม่มีขั้นตอน logout ที่ฝั่งเซิร์ฟเวอร์

    ค่า SECRET ที่ auth.js:5 ใช้ค่า default ถ้าไม่ได้ตั้ง environment variable ใครก็ปลอม token ได้ ต้องตั้งค่าจริงก่อนใช้งาน

    4. ตัวอย่างการบังคับเปลี่ยนรหัสผ่านก่อนใช้งาน

    ผู้ใช้ที่ must_change_password เป็นจริง จะถูกจำกัดให้เรียกได้เพียงไม่กี่ endpoint ทำให้ผู้ใช้ที่เพิ่งได้รับรหัสชั่วคราวต้องเปลี่ยนรหัสก่อน จึงเรียกข้อมูลอื่นไม่ได้

    5. บทบาทและ allow()

    ระบบมี 3 บทบาท ได้แก่ admin, evaluatee และ evaluator การกำหนดสิทธิ์ทำแบบ "ต่อ router": server.js ใส่ allow('admin') ให้ทั้งกลุ่มของ users, periods และอื่น ๆ วิธีนี้ทำให้ไม่ต้องตรวจซ้ำในทุก endpoint

    6. ทำไมข้อความ error ต้องเหมือนกัน

    บทที่ 4: จัดการข้อมูลหลัก (admin)

    ไฟล์ในกลุ่มนี้ใช้รูปแบบเดียวกัน คือ validate แล้ว query แล้วตอบกลับ ถ้าเข้าใจไฟล์หนึ่งจะอ่านที่เหลือได้

    1. CRUD และ HTTP method

    การจัดการข้อมูลทุกตารางใช้รูปแบบ CRUD คือ Create, Read, Update, Delete ซึ่งจับคู่กับ HTTP method ได้แก่ POST, GET, PUT และ DELETE ในโฟลเดอร์ routes ทุกไฟล์จึงมีลำดับเหมือนกัน

    2. โครงสร้างของ route มาตรฐาน

    router.post('/', async (req, res) => {
  const message = validate(req.body);          // 1) ตรวจข้อมูลก่อน
  if (message) return error(res, 400, message);
  const result = await query('INSERT ...', [...]); // 2) เขียนฐานข้อมูล
  ok(res, { id: result.insertId }, 'สร้างแล้ว');     // 3) ตอบกลับ
});

    การตรวจข้อมูลทำที่ฝั่งเซิร์ฟเวอร์เสมอ แม้หน้าเว็บจะตรวจแล้ว เพราะ request สามารถถูกส่งมาจากเครื่องมืออื่นได้

    3. affectedRows: ตรวจว่าแถวถูกแก้จริงหรือไม่

    คำสั่ง UPDATE และ DELETE ไม่ได้บอกว่าเจอแถวที่ตรงเงื่อนไขหรือไม่โดยตรง ผลลัพธ์มีค่า affectedRows ถ้าเป็น 0 แปลว่าไม่พบแถว จึงตอบ 404 ได้ถูกต้อง

    4. ลำดับชั้นของทรัพยากร

    ข้อมูลหลักเป็นลำดับ periods → topics → indicators การสร้างหัวข้อจึงต้องมีรอบที่มีอยู่ก่อน และการสร้างตัวชี้วัดต้องมีหัวข้อก่อน

    5. กฎที่ UNIQUE ทำไม่ได้

    กฎ "ผู้รับหนึ่งคนมีประธานได้หนึ่งคนในรอบเดียวกัน" ไม่ใช่กฎ UNIQUE ธรรมดา เพราะกรรมการคนอื่นต้องเป็น member ได้หลายคน ดังนั้นต้องตรวจในโค้ดก่อนบันทึก (assignments.js:26-33) ซึ่งเป็นตัวอย่างที่ดีของการตัดสินใจว่ากฎควรอยู่ตรงไหน

    6. JOIN และ ORDER BY

    ชื่อผู้รับและชื่อกรรมการไม่ได้อยู่ในตาราง assignments จึงต้อง JOIN กับ users สองครั้ง โดยใช้ alias เช่น e และ v เพื่อแยกว่าอ้างถึงผู้ใช้คนไหน

    การลบผู้ใช้หรือรอบจะลบข้อมูลที่เกี่ยวข้องตาม CASCADE ทันที รวมถึงคะแนน ควรระวังเมื่อเรียก DELETE ใน API จริง

    บทที่ 7: รายงานและการสำรองข้อมูล

    สองไฟล์นี้อ่านข้อมูลจากหลายตาราง จึงต้องดูสิทธิ์การเข้าถึงและวิธีรวมข้อมูล

    1. รายงานคือการรวมข้อมูล

    รายงานต้องนับและรวมข้อมูลจากหลายตาราง ฟังก์ชันรวมที่ใช้บ่อยคือ COUNT และ GROUP BY เช่นนับการมอบหมายแยกตามสถานะ อีกแนวทางคือดึงข้อมูลมาแล้วรวมในโค้ด ทั้งสองแบบพบในไฟล์ reports.js

    SELECT status, COUNT(*) AS total FROM assignments GROUP BY status;

    2. สิทธิ์การดูรายงานรายบุคคล

    ผู้ที่ดูรายงานของผู้รับคนหนึ่งได้คือ admin เจ้าของรายงาน และกรรมการที่ได้รับมอบหมายให้ประเมินคนนั้น การเทียบ id ต้องแปลงค่าจาก URL เป็นตัวเลขก่อน มิฉะนั้นการเทียบจะผิดพลาดเงียบ ๆ

    3. ซ่อนข้อมูลตามสถานะ

    เจ้าของเห็นคะแนนของกรรมการได้เฉพาะเมื่อยืนยันแล้ว ฟังก์ชันจึงล้างคะแนนและความเห็นของกรรมการที่ยังไม่ยืนยันก่อนส่งให้เจ้าของ นี่คือการควบคุมข้อมูลตามสถานะ ไม่ใช่การปฏิเสธคำขอทั้งหมด

    4. Backup และ restore
